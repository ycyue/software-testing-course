# 第 1 章：软件测试入门

## 这一章解决什么问题

很多人第一次听到“软件测试工程师”，会把它理解成“把软件点一遍，找出 Bug”。找 Bug 的确是测试工作的一部分，但软件测试还包括理解需求、发现需求问题、验证产品是否满足用户需要、评估质量和提供上线风险信息。

本章的任务，是先建立正确的测试世界观，再学习后续的需求、用例、Web、HTTP、SQL、接口和自动化。

## 学习目标

完成本章后，你应该能够：

- 用自己的语言解释软件测试；
- 理解测试不等于单纯找 Bug；
- 说明为什么软件需要测试；
- 区分 Testing、QC 和 QA 的基本含义；
- 理解软件质量不仅是“功能能用”；
- 解释七大基本测试原则；
- 描述初级测试工程师的基本工作流程；
- 说明测试工程师与开发工程师的主要区别；
- 认识常见测试岗位和发展方向。

## 前置知识

无需软件测试、编程或计算机专业知识。

## 场景导入：登录失败，这算测试吗？

假设 MiniShop 有一个登录页面。需求是：用户输入正确手机号和密码后，可以进入商城首页。

开发完成后，你输入：

- 手机号：13800138000
- 密码：Test1234（教学示例，与第 19 章项目数据相同；不是生产密码）

点击登录，结果却是“登录失败”。你发现了一个缺陷，这当然属于测试。

## 1.1 软件测试到底是什么 ⭐⭐⭐

上面那种“运行起来再点”的活动是测试。但如果你在开发开始前阅读需求，发现“密码连续输错 20 次怎么办？”没有说明；或者发现“账号被冻结后什么时候恢复？”没有定义，这同样是测试活动的重要部分。此时甚至还没有运行程序，测试已经帮助团队发现了问题。

### 测试不只是运行软件

软件测试可以理解为：

> 通过一系列活动发现问题、验证需求，并为软件质量和风险提供信息。

更完整地说，测试不仅用于发现失效和缺陷，也用于预防缺陷、验证规定的需求、确认系统是否满足用户与业务需要，并为相关人员的决策建立信心和提供信息。测试不能保证软件“绝对正确”，它只能在给定范围、环境、时间和数据下提供证据。

测试活动既可以是动态的，也可以是静态的。

动态测试：运行软件后进行测试，例如打开登录页、输入账号、点击登录、检查结果。

静态测试：不执行被测程序，通过阅读需求、设计、代码或其他工作产品发现问题，例如在需求评审中发现退款规则互相矛盾。

因此，软件还没有开发完成，并不意味着测试工程师什么都不能做。需求评审就是测试提前介入的典型方式。

### 测试要回答哪些问题？

测试工程师经常需要回答：

- 功能做对了吗？
- 需求本身合理、完整、清晰、可测试吗？
- 异常和边界情况会怎样？
- 不同权限的用户能做什么？
- 数据有没有写错？
- 这次修改会不会影响其他功能？
- 当前版本是否适合上线？
- 还有哪些风险没有解决？

所以测试不是单纯寻找错误，而是不断获取关于软件质量的信息。

## 1.2 为什么需要软件测试 ⭐⭐⭐

### 原因一：人会犯错

软件要经过需求分析、设计、编码、配置和数据操作。任何环节都可能产生错误。

例如 MiniShop 规定库存范围为 0～9999 件，代码却实现成 0～99999。一个多写的数字，就可能造成库存数据异常。

### 原因二：功能组合会快速增加复杂度

注册、登录、商品和购物车单独看可能都不复杂，但组合后会受到用户类型、库存、权限等因素影响。电商领域还常见优惠券、支付和订单状态机，那些能力**不是** MiniShop v1.0 的范围，本章只用它们说明“组合会变复杂”。

因此，不能只靠开发工程师“随便点几下”就覆盖所有重要场景。

### 原因三：关注点不同

开发工程师首先会思考“如何实现功能”，测试工程师会继续追问“在各种重要情况下是否符合预期”。

年龄输入框要求 18～60 岁时，除了测试 25，还应考虑：

18、60、17、61、空值、18.5、abc、-1 和极大数值。

这类从正常路径扩展到异常、边界和组合场景的思维，会贯穿整套课程。

### 原因四：缺陷成本可能很高

缺陷可能导致无法登录、重复扣款、数据丢失、隐私泄露、服务宕机、财务损失和用户流失。

测试的价值不只是“找到了几个 Bug”，而是帮助团队降低产品失败的风险。

## 1.3 Testing、QC 和 QA ⭐⭐

不要先死记复杂定义，可以先记住一个模型：

- QA（Quality Assurance，质量保证）：关注整个过程如何建立和改进质量；
- QC（Quality Control，质量控制）：关注产品是否达到质量要求；
- Testing（软件测试）：通过评审、分析、设计、执行和验证等活动获取质量信息。

软件测试通常是质量控制的重要手段，但 QA 不等于测试工程师的另一个英文名字。现实招聘中，有些公司会把 QA Engineer 作为测试岗位名称，因此要区分理论概念和企业岗位命名。不同组织对 QA、QC 和测试职责的边界可能不同，岗位名称不能自动代表完整的质量职责范围；入职时应以团队实际分工、流程和交付责任为准。

## 1.4 什么叫软件质量 ⭐⭐

“功能能用”不等于“质量好”。

假设 MiniShop 可以下单，但首页需要 20 秒才能打开、Safari 页面错位、系统随机崩溃、密码明文显示、手机端按钮无法点击，这个产品仍然存在明显质量问题。

ISO/IEC 25010:2023 的产品质量模型包含九个质量特性。下面的中文名称采用本课程教学译法；正式项目如有组织术语表，应以组织约定为准：

1. 功能适合性（Functional Suitability）
2. 性能效率（Performance Efficiency）
3. 兼容性（Compatibility）
4. 交互能力（Interaction Capability）
5. 可靠性（Reliability）
6. 信息安全性（Security）
7. 可维护性（Maintainability）
8. 灵活性（Flexibility）
9. 安全保障性（Safety）

这里的 Security 与 Safety 不是重复概念。Security 主要关注信息和系统免受未授权访问、使用、修改或破坏；Safety 关注产品在使用时是否会造成对人员、财产或环境不可接受的风险。普通电商测试更常直接接触 Security；医疗设备、汽车和工业控制等系统通常会对 Safety 提出更严格要求。

初学阶段不需要背完整标准，但要知道质量是多维度的：

- 功能：是否完成正确的业务结果，例如正确密码能否登录、购物车数量是否按规则保存；
- 性能：响应速度、吞吐能力和资源消耗是否满足场景要求；
- 兼容性：不同浏览器、设备或系统组合是否正常；
- 交互能力：用户是否容易理解和操作；
- 可靠性：系统能否稳定工作；
- 信息安全性：账号、密码、数据和权限是否得到保护。

具体性能阈值必须以项目需求、协议或组织标准为准，不能把某个示例数字当成行业统一标准。

## 1.5 软件测试七大基本原则 ⭐⭐⭐

### 原则一：测试只能证明缺陷存在，不能证明缺陷不存在

执行 100 次测试没有发现问题，只能说明在已经覆盖的范围内没有发现已知问题，不能证明系统绝对没有缺陷。

更专业的表达是：

> 当前测试范围内未发现阻塞上线的已知严重缺陷。

### 原则二：穷尽测试是不可能的

密码允许 8～20 个字符，但可能的字符组合数量极大，不可能逐一测试全部输入。

因此需要等价类、边界值、风险分析和优先级，把有限资源集中到更有代表性的场景。

### 原则三：尽早测试可以节省时间和成本

需求评审时发现退款规则没有写清楚，通常只需要补充规则；如果等到前端、后端、数据库和测试用例都完成后才发现，返工成本会明显增加。

所以测试应尽早介入开发生命周期。需求和设计阶段的评审就是静态测试的一部分。

### 原则四：缺陷具有集群性

缺陷通常不会平均分布。假设过去几个版本中，支付模块发现 21 个问题，而注册模块只有 2 个，那么下一轮测试应结合风险给支付模块更多关注。

这也是风险驱动测试的重要依据。

### 原则五：测试会逐渐失效（测试会磨损）

如果半年内只重复执行完全相同的 100 条用例，它们可能很适合发现过去的问题，但对新功能、新数据和新风险的发现能力可能下降。

ISTQB CTFL 4.0.1 将这一原则称为“测试会磨损（tests wear out）”；旧资料也常称“杀虫剂悖论”。这不代表回归测试没有价值。稳定的自动化回归测试仍然重要，只是已有测试也需要根据代码、数据、使用方式和风险变化定期评估、更新和补充。

### 原则六：测试依赖上下文

测试银行系统、小游戏、电商系统和内部管理系统时，风险和重点不可能完全一样。

银行系统可能重点关注金额、权限、数据一致性和安全；小游戏可能更关注操作体验、性能和兼容性。

不存在适用于所有软件的万能测试清单。

### 原则七：无缺陷谬论

即使系统完全按照需求实现，所有已知缺陷也被修复，用户仍然可能认为它不好用，或者不能解决真正的问题。

“符合规格”不等于“满足用户需要”。因此测试既要关注验证（Verification），即规定的需求是否得到满足；也要关注确认（Validation），即产品是否满足预期用途和用户需要。实际中文资料对这两个词的译法可能不同，工作中应同时说明英文术语和具体含义，避免只凭中文词面判断。

### 七大原则总结

1. 测试不能证明绝对无缺陷；
2. 不可能把所有情况全部测完；
3. 越早测试通常越有利；
4. 缺陷往往集中在某些区域；
5. 测试用例需要持续更新；
6. 测试方法依赖项目背景；
7. 符合规格、修完已知缺陷，仍可能不满足用户真正需要（无缺陷谬论）。

## 1.6 测试工程师每天在做什么 ⭐⭐⭐

一个典型流程可能是：

```mermaid
flowchart LR
    A[需求提出] --> B[需求评审]
    B --> C[测试设计]
    C --> D[执行测试]
    D --> E[提交 Bug]
    E --> F[验证修复]
    F --> G[回归测试]
    G --> H[输出风险信息]
```

这不是所有团队都完全相同的固定流程，但它能帮助初学者建立一个基本模型。真实项目中，部分活动可能并行进行，测试也可能在需求和设计阶段提前介入。

以“购物车数量修改”为例，测试工程师会确认：

- 最少可以买几个？
- 最多可以买几个？
- 超过库存怎么办？
- 库存为 0 怎么办？
- 快速连续点击加号会怎样？

发现库存只有 10 件却能添加 11 件时，Bug 报告至少要包含环境、前置条件、复现步骤、实际结果、预期结果以及必要的截图和日志。修复后要验证这个问题，并回归购物车删除、结算等相关功能。

## 1.7 测试工程师和开发工程师有什么不同 ⭐⭐⭐

| 维度 | 开发工程师 | 测试工程师 |
| --- | --- | --- |
| 主要职责 | 构建和维护系统 | 通过测试活动评估质量、发现风险并提供信息 |
| 常见问题 | 如何实现 | 哪些情况可能出问题 |
| 需求关注 | 如何落地实现 | 是否完整、清晰、可测试 |
| 异常关注 | 实现必要处理 | 系统性验证异常、边界和组合 |
| 代码要求 | 通常较高 | 根据岗位不同，从少量脚本到测试开发均有 |

这不是“开发制造 Bug、测试专门抓错”的对立关系。现代研发强调团队共同对质量负责。

## 1.8 常见软件测试岗位 ⭐⭐⭐

### 功能测试工程师

重点是需求分析、测试用例、Web/App 测试、Bug 管理和回归测试，适合作为零基础进入测试领域的起点之一。

### 接口测试（常见岗位能力）

重点是 HTTP、API、Postman、SQL 和数据验证。实际工作中接口测试通常是测试工程师的重要能力，而不一定对应一个独立岗位；判断岗位内容时应以招聘说明和团队分工为准。

### 自动化测试工程师

重点是 Python 或 Java、pytest、requests、Selenium 或 Playwright，以及自动化框架设计。通常需要比纯功能测试更强的编程能力。

### 性能测试工程师

关注响应时间、吞吐量、并发、CPU、内存和系统瓶颈，常见工具包括 JMeter。

### 测试开发工程师

通常简称“测开”，可能负责自动化平台、测试框架、测试工具、CI/CD、效能平台和质量基础设施，需要更强的软件工程能力。

## 1.9 软件测试职业发展 ⭐⭐

一种常见路线是：

初级测试 → 功能测试 + 接口 + SQL + Linux → Python/自动化 → 自动化测试或测试开发 → 高级测试、测开或质量工程。

也可以向测试负责人、测试经理、性能测试、安全测试、DevOps、SDET 和研发效能等方向发展。

> 找 Bug 是软件测试的重要部分，但软件测试不仅是运行程序寻找 Bug。测试还包括需求评审、测试分析与设计、风险评估、验证需求以及为团队提供软件质量信息。测试既可以在程序运行后进行，也可以在开发之前通过评审等静态方式发现问题。

## 常见错误

1. 测试的目标是证明软件没有 Bug。  
   修正：测试用于发现缺陷、评估质量和降低风险，不能证明绝对无缺陷。

2. 测试必须等开发完成才能开始。  
   修正：需求、设计阶段就可以通过评审等静态测试活动提前介入。

3. 测试工程师就是一直点页面。  
   修正：还包括需求分析、测试设计、数据准备、接口、日志、风险和沟通。

4. 测试和开发是对立关系。  
   修正：职责不同，但质量目标一致。

5. 功能正常就说明质量很好。  
   修正：还要考虑性能、可靠性、安全性、兼容性和交互能力。

## 面试角度 ⭐⭐⭐

### 什么是软件测试？

测试是一组用于发现缺陷、验证需求并评估软件质量和风险的活动。它不仅包含运行软件，也包括需求评审等静态活动，目的是帮助团队更可靠地判断软件质量和发布风险。

### 软件测试的目的是什么？

发现缺陷是重要目的之一，同时还要验证需求、评估产品质量、降低上线风险，并为项目决策提供质量信息。

### 测试有哪些基本原则？

重点理解七条原则，不要只背诵名称。回答时要能结合实际场景说明穷尽测试、尽早测试、风险集中和上下文差异。

### 测试和开发有什么区别？

职责和关注点不同，但不是互相对立；软件质量是整个团队共同负责的目标。

## 练习答案

1. C。测试不仅是运行程序找 Bug，还包括评审、分析、设计和质量评估。

2. 属于测试。它可以提前发现需求中的歧义、遗漏和边界不明确问题。

3. 不能简单认为质量好。功能可能正确，但性能效率存在严重问题。具体是否达到要求要以项目目标和场景阈值判断。

4. 不能。测试可以发现缺陷存在，但不能证明所有缺陷都不存在。

5. 输入组合数量巨大，不可能全部测试，对应“穷尽测试是不可能的”。

6. 应结合风险增加支付模块测试，体现“缺陷具有集群性”。

7. 对应“无缺陷谬论”：符合规格不等于满足用户真正需要。

8. 参考答案：开发和测试职责不同，但共同目标是交付高质量产品。测试发现问题是为了帮助团队尽早识别风险，而不是证明开发能力不行。合理表达即可。

## 本章总结

本章需要真正理解五件事：

1. 软件测试不只是找 Bug。
2. 测试可以在代码出现之前开始。
3. 测试不能证明软件绝对没有 Bug。
4. 软件质量包括功能、性能、可靠性、安全、兼容性和交互等多个方面。
5. 测试工程师提供的是关于软件质量和风险的信息。

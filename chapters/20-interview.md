# 第 20 章：软件测试面试

> **一句话核心：** 面试是在讲你做过的观察、判定和证据，不是背名词。

> 重要级别：⭐⭐⭐ 必须掌握  
> 主案例：MiniShop 个人软件测试实践项目

## 这一章解决什么问题

第 19 章已经有一套能跑的 MiniShop v1.0 和 pytest、BUG-001、PRD。面试官不会先打开你的仓库，他们会问：你是谁、项目做了什么、理论会不会、碰到争议怎么办。

答不好通常不是“不会测”，而是：**没有先给结论、举例对不上仓库、把课程约定说成全球标准、把个人项目说成公司系统。**

本章把高频问题收成可说出口的答案。统一结构是课程要求的：

**结论 → 原理 → 场景 → 示例 → 边界。**

示例必须能指向 `project/minishop/` 里已有的证据。不要临场编造订单状态、生产压测或企业职级。不会的题目先说不会，再说你打算怎么查。

## 学习目标

完成本章后，你应该能够：

- 用五段结构回答，而不是先背定义后找不到重点；
- 在约一分钟内做自我介绍，并在约两分钟内介绍 MiniShop；
- 回答测试理论、需求分析、用例与方法、缺陷的常见追问；
- 回答 Web、HTTP、接口、SQL、Linux、Python、pytest 的常见追问；
- 在项目深挖时引用 PRD、qty=10/11、BUG-001、38 passed / 1 xfailed；
- 处理行为面试（争议、漏测、不会的题），不夸大、不攻击同事；
- 识别一套“听起来很满、其实会翻车”的答法。

## 前置知识

- 已完成第 19 章，能启动 MiniShop 并讲清范围与非范围；
- 已完成第 1～18 章中对应知识点；本章是面试表达，不新造技术规则；
- 不要求有企业实习。没有实习就用个人项目，不要编公司。

## 场景导入：先报公司，再被问订单状态

面试官：“介绍一下你的项目。”  
错误开头：“我在某电商公司负责 MiniShop 全链路，把订单从待支付测到已完成……”  
接着被问状态机、支付渠道、QPS 指标——仓库里都没有。

应改成：

1. 结论：这是个人实践项目 MiniShop v1.0；
2. 原理：用来把需求、用例、接口和缺陷收成可展示证据；
3. 场景：购物车数量与库存；
4. 示例：qty=11 返回 400，pytest 38 passed、1 xfailed（空搜索 BUG-001）；
5. 边界：无支付、无订单状态字段，不是公司系统。

## 20.1 为什么必须用这五段 ⭐⭐⭐

![面试五段：结论、原理、场景、示例、边界](assets/diagrams/ch20-five-beats.png)


生活类比：问“火怎么灭”，先说“先撤离再报火警”，不要先背燃烧条件。

面试官时间短，先听你的判断。原理证明你不是背的。场景证明你用过。例子必须可核对。边界避免把课程约定说成宇宙真理。

错误例子：把七大原则从第一条背到第七条，不问这题要哪一条。  
边界例子：P0 先声明“这是我们课程的优先级约定”。

不会时：结论先说“这个我没在项目里做过”；原理说“我知道该查哪类资料”；场景说“如果入职后遇到”；示例说“我会先看项目文档”；边界说“现在不能装会”。

## 20.2 自我介绍 ⭐⭐⭐

约 45～90 秒。结构仍是五段，压缩成口语。

结论：我是转/应届初级测试，能独立完成功能、接口和 SQL 核对，用个人项目 MiniShop 练过一轮完整测试。  
原理：测试是获取质量信息、降低风险，不是只点页面。  
场景：从需求评审到 pytest 回归。  
示例：库存不得超卖；空搜索记了 BUG-001。  
边界：没有企业项目就如实说；不讲支付和状态机。

口播示例（请改成你的真实背景，不要抄学历和年限）：

> 我是零基础学测试的候选人。我会按需求写用例、提缺陷，能用 DevTools、SQL 和接口做核对。个人项目 MiniShop v1.0 覆盖注册、登录、购物车库存和创建订单，pytest 有 38 通过、1 条预期失败对应空搜索缺陷。我没有公司实习，项目是自己的练习仓库，不是某电商的核心系统。希望做功能测试，并在团队里继续补接口自动化。

不要：编年限、编带人、背一长串工具名却举不出一条用例。

## 20.3 项目介绍 ⭐⭐⭐

约两分钟。问“你的项目”时用这个，而不是把自我介绍再念一遍。

结论：个人测试实践 MiniShop v1.0；可运行前后端 + 测试文档。  
原理：先定范围再测；证据必须能在仓库找到。  
场景：购物车数量 = 正整数且 ≤ 当前库存。  
示例：注册 201 无 token；qty=10 允许 / 11 拒绝；订单只返回 id；B 读 A 的订单 403；空搜索 = BUG-001。  
边界：现行即 `/api/` 与 PRD（旧 `/login` + qty=1 教学桩已删除）；无生产压测。

对着计时自己说满 90～120 秒。用上面提纲组句，数字以本机仓库为准。不要把 20.2 再念一遍，也不要把本节当口播背。

被追问“你开发的还是测试的”：结论是测试为主，仓库里的实现是为了让测试可运行；不冒充全栈开发岗。原理：面试要分清交付物是测试材料还是产品研发。场景：被问“后端是你写的吗”。示例：我交付 PRD、用例、pytest 和 BUG-001。边界：教学代码可运行不等于全栈开发岗。

被追问数据：种子账号 `13800138000`，SKU-DEMO-001 库存 10。不要把教学密码在面试里反复大声报给全场；说“教学弱口令，仅本地”即可。

## 20.4 测试理论 ⭐⭐⭐

20.4～20.14 是答题提纲，不是背稿。每个标签一行关键词，面试时你自己组句。工作实战不得连续粘贴两句以上本节原文。被问到没做过的域，先说项目里没做过。

### 软件测试是什么？

结论：静态 + 动态 → 质量与风险信息。  
原理：人会错；组合爆炸；测的关注点 ≠ 实现。  
场景：不能只看 MiniShop 首页打开。  
示例：qty=11 对接口、页面、库。  
边界：没找到 ≠ 没有。

### Testing、QC、QA？

结论：Testing = 获取信息；QC = 产品是否达标；QA = 过程如何保障。  
原理：测试常是 QC 手段；QA ≠ 测试的另一个英文名。  
场景：招聘 QA Engineer 可能就是测试岗。  
示例：评审需求 = 测试活动，也可服务 QA。  
边界：入职看分工，不看职称翻译。

### 举一条测试原则。

结论：说名字 + 你的理解；不要默写七条。常用：显示缺陷存在 / 穷尽不可能 / 尽早介入。  
原理：ISTQB 等材料里的经验规律。  
场景：pytest 38 passed / 1 xfailed（BUG-001 仍开放）。  
示例：「没发现 Bug 就没 Bug」是错的。  
边界：原则不是拒测某模块的借口。

### 测试要等开发全部完成才能开始吗？

结论：不必；需求和设计就可评审。  
原理：越早发现往往越便宜。  
场景：第 4 章静态测试。  
示例：评审阶段就能抓歧义。  
边界：动态执行仍要可运行版本。

## 20.5 需求分析 ⭐⭐⭐

结论：需求 → 可测试规则、风险、待确认；不是抄 PRD。  
原理：歧义 / 遗漏 / 矛盾 → 测完也不知道对不对。  
场景：「用户可以改购物车数量」。  
示例：问最小、能否超库存、库存以何时为准；v1.0：1≤qty≤当前库存，等于允许。  
边界：没确认的状态机不要写进用例。

追问“不可测试的需求”：

结论：缺可观察结果或条件。  
原理：没有可核对预期就无法判定通过。  
场景：评审搜索规则。  
示例：「搜索要智能」没有口径。  
边界：先要求改写成可验证句。

## 20.6 测试方法与用例 ⭐⭐⭐

### 你怎么设计用例？

结论：先拆测试点；再用等价类、边界、判定表、场景；按风险取舍。  
原理：穷尽不可能；用模型提高命中率。  
场景：购物车数量。  
示例：1 / 10 / 11 / 0 / 负数 / 空 / null / 字符串。  
边界：方法服务对象；不为用判定表而硬套。

### P0 是什么？

结论：本课程：核心主路径或阻塞基本测试的**用例优先级**。  
原理：优先级 = 执行顺序，≠ 缺陷严重程度。  
场景：注册、登录、合法改数量、创建订单。  
示例：`docs/test-cases.md`：`TC-REG-001` / `TC-LOGIN-001` / `TC-CART-002`（qty=10）/ `TC-ORDER-001`。  
边界：**不是全球同一套数字**；也不是 Severity。入职先问定义。

## 20.7 Bug ⭐⭐⭐

结论：报告要能复现：环境、步骤、预期、实际、证据。  
原理：无法复现就无法修复和验证。  
场景：空搜索。  
示例：BUG-001，`GET /api/products?keyword=` 返回三件；PRD 不许把全量当搜索结果。  
边界：严重程度 ≠ 用例 P0；状态名因工具而异。

“和开发吵起来怎么办”见 20.16。  
“没找到 Bug 是不是没价值”：

结论：不是。通过的用例也是信息。  
原理：只能证明缺陷存在，不能证明不存在。  
场景：主路径通过，空搜索仍不符合 PRD。  
示例：38 passed / 1 xfailed（BUG-001）。  
边界：没发现 ≠ 没有；也不等于对用户有价值。

---

## 20.8 Web ⭐⭐⭐

结论：测用户路径：表单、登录态、权限、提示；不只「页面能打开」。  
原理：接口对了，按钮也可能没绑事件。  
场景：MiniShop 登录页。  
示例：错误密码提示；普通用户调 `/api/admin/*` → 403（`/admin.html` 仍可能 200）。  
边界：兼容矩阵按用户和风险裁剪。

Cookie、Session、Token：

结论：不同层次，常同时出现；不是三选一产品。  
原理：Cookie 保存发送；Session 服务端会话；Token 凭证；Bearer 出示方式。  
场景：登录成功后既有 Cookie 又有 JSON token。  
示例：v1.0 既 `Set-Cookie` 又返回 token；后续 API 用 `Authorization: Bearer`。  
边界：以文档为准；不要答「现在都用 Token」。

---

## 20.9 HTTP ⭐⭐⭐

结论：按方法语义、状态码、头和 Body 测；不按「GET 不安全、POST 安全」。  
原理：HTTP safe = 语义不改资源，不是保密；保密看 TLS。  
场景：登录用 POST（改会话；密码不放 query）。  
示例：`POST /api/login`。  
边界：不要说 GET 更安全所以登录必须 GET。

401 与 403：

结论：常见约定：未认证 vs 已认证无权限。  
原理：先「你是谁」，再「能不能做」。  
场景：无凭证改购物车；用户 B 读用户 A 的订单。  
示例：无凭证（无 Bearer **且** 无 Cookie）下单 401；仅缺 Authorization 仍可能 201。B 读 A 的订单 403。  
边界：项目可能混用，以契约为准；缺陷里两者都记。

---

## 20.10 接口 ⭐⭐⭐

结论：按契约发请求；核状态码、JSON、副作用。  
原理：缺字段、null、空串、错误类型不是同一条输入。  
场景：`POST /api/cart/items`。  
示例：qty 为 null / `""` / `"1"` / 11 在 v1.0 均应失败（11 = 超库存）。  
边界：REST ≠ JSON 的别名；接口绿不能取消页面测；**接口自动化 ROI 不是永远最高**。

幂等：

结论：多次相同请求的效果与一次相同。  
原理：创建类 POST 默认会新增资源。  
场景：连续点两次下单。  
示例：v1.0 两次 `POST /api/orders` → 两个 id。  
边界：若以后需求要求幂等，期望要改。

---

## 20.11 SQL ⭐⭐⭐

结论：用查询证明页面 / 接口与库是否一致。  
原理：显示 11 ≠ 库里是 11。  
场景：授权教学库。  
示例：JOIN 用户-购物车-商品，见 `evidence/sql/seed-join.txt`；以当时查询为准。  
边界：只在授权库改数；先 SELECT；不用 `=` 判断 NULL。

---

## 20.12 Linux ⭐⭐⭐

结论：授权测试机上看日志、磁盘、进程；脱敏 curl 复现。  
原理：500 的证据常常在服务端。  
场景：qty=11 被拒。  
示例：日志 `inventory reject sku=SKU-DEMO-001 stock=10 qty=11`。  
边界：`free -h` 是 Linux；macOS 失败 ≠ 产品内存缺陷。不对未授权机器扫描。

---

## 20.13 Python ⭐⭐⭐

结论：测数据、写小脚本；不是转开发。  
原理：JSON null → None；缺键和 null 用 `in` 区分。  
场景：解析登录 Body 取 token。  
示例：第 15 章；不要 `eval` 解析 JSON。  
边界：`if qty:` 会把 0 当成没有数量。

---

## 20.14 pytest（技能第二梯队，面试被问到时按五段答）⭐⭐⭐

结论：测试函数 + assert 做可重复检查；fixture 准备 token；parametrize 展开输入。  
原理：收集 `test_`；断言失败会改写左右值。  
场景：MiniShop `tests/`。  
示例：本机条数（审查 38 passed / 1 xfailed 对 BUG-001）。  
边界：autouse token 会毁掉 401 用例；pytest 绿不是性能结论。

## 20.15 项目深挖 ⭐⭐⭐

面试官会沿着你的介绍往下挖。只回答仓库里有的东西。

| 追问 | 结论要点 | 证据 | 边界 |
| --- | --- | --- | --- |
| 测了哪些接口？ | `/api/register`（201 无 token、占用 409）、`/api/login`、products、cart、orders、admin | OpenAPI、pytest | 注册成功不自动登录 |
| 库存规则？ | 正整数且 ≤ 当前库存，等于允许 | PRD R-CART-10 | 曾有 qty=1 教学桩，已删除；现行跟 PRD |
| 有什么 Bug？ | 空搜索返回全量 | BUG-001 | 仍开放，不写成已修复 |
| 自动化多少条？ | 以你最近一次 pytest 为准 | 审查为 38 passed / 1 xfailed | 条数以本机输出为准 |
| 订单状态？ | v1.0 不定义，响应无 status | PRD 非范围 | 不编状态名 |
| 你做过性能吗？ | 只学了指标和纪律，项目未加压 | 第 18 章、测试报告 | 无 SLA、无生产压测 |
| 你写过后端吗？ | 仓库有教学实现，我的交付是测试材料 | 不要冒充开发岗 | 教学代码 ≠ 开发岗 |

被问到支付、优惠券、APP、微服务治理：结论是“v1.0 没有，我没有做过”，再补“如果要测我会先要契约和数据”。不要编。

## 20.16 行为面试 ⭐⭐⭐

行为题仍用五段，场景换成你真实做过的事。没有企业经历，就用 MiniShop、课程练习、小组作业。不要借别人的故事。有人把行为题叫 STAR（情境、任务、行动、结果）。本课不另背一套：五段里的「场景」对应情境，「示例」对应你做了什么和拿出的证据，「边界」对应学到什么或下次怎么改。先给结论。

### 和开发对缺陷有分歧？

结论：先对数据和复现，不对人。  
原理：争议缺陷要回到需求、日志和库。  
场景：空搜索算不算缺陷。  
示例：我拿出 PRD R-SEARCH 和实际三件商品的响应，标成开放缺陷而不是口头吵赢。  
边界：需求真改了就要改用例，不把过时 PRD 当武器。

### 漏过一个 Bug 怎么办？

结论：先承认，补复现和回归，再改检查单。  
原理：漏测是过程信息，不是人格否定。  
场景：若只测了 qty=11 忘了空搜索。  
示例：用 BUG-001 说明漏了会怎样。  
边界：不要把别人的线上事故说成自己的英雄故事。

### 不会的题？

结论：直接说不会或只了解到哪一步。  
原理：装会比不会更致命，深挖会穿。  
场景：被问 JMeter 分布式。  
示例：“我能解释负载和压力，没搭过分布式，不能说精通。”  
边界：说完不会，可以补“我打算看官方手册哪一节”，不要空白沉默到死。

### 为什么做测试 / 抗压 / 加班？

结论：对质量信息感兴趣、能接受细节工作；加班以事实和边界回答，不表演。  
原理：行为题看诚信和协作。  
场景：用你真实的学习节奏。  
示例：完成 MiniShop 文档比通宵背工具名更说明态度。  
边界：不攻击前公司或前同学；不承诺违法违规的加班或未授权测试。

必做：用自己的话写。自我介绍、项目介绍各对着计时说一遍。不准整段抄本章口播。

## 面试角度 ⭐⭐⭐

本章本身就是面试训练。再记三条元问题：

### 面试官最想听什么？

结论：判断、证据、边界，不是词表。  
原理：面试官要的是你会不会测，不是词表长度。  
场景：被问购物车规则。  
示例：先说 qty=11 应拒绝，再提日志和 pytest。  
边界：工具名只能当配料。

### 没有实习怎么面？

结论：用个人项目和课程材料，诚实说明。  
原理：深挖要对得上仓库，编公司会穿。  
场景：被问实习公司业务量。  
示例：指得清 PRD、BUG-001、如何启动。  
边界：不要用“保密协议”挡一个不存在的公司项目。

### 被问倒了怎么收场？

结论：承认范围，给下一步，停止编造。  
原理：装会比不会更容易被追穿。  
场景：被问 JMeter 分布式或生产 QPS。  
示例：“性能我只做过指标学习，MiniShop 没有加压报告。”  
边界：收场后不要再补一段假数据。

# 第 2 章：软件研发流程与测试的位置

## 学习目标

理解 SDLC、STLC、瀑布模型、V 模型、Agile、Scrum、测试左移、测试右移和 Git 基础，并能说明测试何时介入项目。

## 2.1 软件从需求到上线

软件通常经历需求提出、分析评审、设计、开发、测试、发布和维护。真实项目中这些活动可能迭代、重叠或并行。测试不只在开发完成后出现，需求评审、设计评审、测试分析和代码评审都能提前发现问题。

## 2.2 团队角色

产品负责业务目标，设计负责交互和视觉，开发负责实现，测试负责测试分析、设计、执行、缺陷验证和风险反馈，运维或平台团队负责环境与运行支持。角色边界因组织而异，质量是团队共同责任。

## 2.3 SDLC 与 STLC

SDLC 是软件开发生命周期，关注软件从需求到维护的整体过程。STLC 是软件测试生命周期，关注需求分析、测试计划、测试设计、环境准备、执行、缺陷管理、回归和测试总结。STLC 是测试视角，不是脱离开发的另一套项目流程。

## 2.4 瀑布模型与 V 模型

传统阶段式流程中，动态测试执行往往集中在编码后的测试阶段，但需求、设计等工作产品可以更早评审。瀑布模型阶段边界清晰，但变化成本可能较高。V 模型强调开发活动与测试活动的对应：需求对应验收测试，系统设计对应系统测试，架构设计对应集成测试，详细设计对应单元测试。V 模型帮助我们理解测试需要提前规划，不要求所有团队机械照搬。

## 2.5 Agile 与 Scrum

敏捷强调短周期交付、持续反馈、拥抱变化和团队协作。Scrum 常见角色包括 Product Owner、Scrum Master 和 Developers，以 Sprint 为周期，常见活动包括计划、Daily Scrum、评审和回顾。测试工程师应参与需求澄清、验收标准讨论、测试设计、执行和回归，而不是只在 Sprint 末尾工作。

## 2.6 测试左移与测试右移

测试左移是把质量活动提前到需求、设计和开发阶段，例如需求评审、静态分析、代码评审和开发阶段自动化测试。测试右移关注发布后的监控、日志、灰度、线上反馈和故障复盘。右移不是把未完成的测试推给用户，也不取代发布前测试。

## 2.7 Git 基础

working tree 是工作区，commit 是版本记录，branch 是开发线，merge 是合并，pull 是获取远端更新，push 是上传提交。常见流程是修改文件、git status、git add、git commit、git push。commit 和 push 不是一回事。

## MiniShop 实战

新增优惠券需求时，测试工程师应在评审阶段询问：适用商品是什么、有效期如何计算、最低金额是多少、能否重复使用、退款后如何处理、谁有管理权限。开发提测后执行冒烟和功能测试，发布后结合日志和错误反馈继续观察。

## 常见错误

1. 测试必须等开发完成：错误，需求和设计阶段就可以静态测试。
2. V 模型就是瀑布：错误，V 模型重点是开发与测试活动的对应。
3. 敏捷等于没有计划：错误，敏捷仍需要目标、优先级和验收标准。
4. 测试右移就是上线后才测试：错误，右移是运行阶段质量反馈的补充。
5. push 等于 commit：错误，commit 记录版本，push 上传远端。

## 练习

1. SDLC 和 STLC 分别关注什么？
2. 为什么瀑布流程中测试不必等到开发结束？
3. V 模型中需求通常对应哪类测试？
4. 左移和右移各举两个例子。
5. 为优惠券需求提出三个评审问题。

## 练习答案

1. SDLC 关注整体开发生命周期，STLC 关注测试活动生命周期。
2. 因为需求和设计等工作产品可以提前评审。
3. 验收测试。
4. 左移可包括需求评审和代码评审；右移可包括监控和日志分析。
5. 例如有效期、最低金额、退款后处理；合理且具体即可。

## 总结

测试不是研发流程末尾的验收工序，而是贯穿需求、设计、开发、测试、发布和维护的质量活动。

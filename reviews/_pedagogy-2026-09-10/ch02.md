## 总判

读者跟得上「测试不必等代码写完」，练习 1～8 能自检。但开篇场景只有一句，2.8 是填满的教师表，Git 无第一帧，STLC/Scrum 定义长于例子。补走读、把 2.8 改成带路径填空、给 Git 第一帧后可发布。

## 阶梯

- 章内坡度：2.1 地图 → 模型 → Scrum/左移右移 → 提测冒烟确认回归，方向对。缺口是「场景导入」只有三句，真正的购物车走读要到 2.8，导致 2.2、2.5 先吞一表术语。Git（2.9）从概念章突然切到 CLI，中间没有「为什么证据要进版本库」的半步。练习 1～8 是识别/口述，练习 9 才动手，符合「识别 → 改一处 → 能交代」，但指定工作实战 2.8 本身没有让读者填。
- 相对上一章：开篇「第 1 章说明了测试不只是开发完成后找 Bug」承接清楚；第 1 章文末预告的提测 / Sprint / 回归 / 上线，本章都有对应节。前置要求的静态/动态与七原则，第 1 章已教。第 1 章已把 Confirmation 和 Validation 的「确认」拆开，2.7 定义确认测试时未回指这一句，零基础仍可能把两处「确认」焊在一起。
- 相对下一章：没有把第 3 章主课（六条分类轴）讲完。冒烟 / 确认 / 回归放在 2.7 是对的，第 3 章 3.6–3.7 已改成挂到「目的轴」。V 模型表点名了验收 / 系统 / 集成 / 组件测试却不解释级别含义，也没写「级别定义见第 3 章」，读者会以为本章就要背这四个词。
- 星级是否诚实：2.3 角色、2.9 Git 标 ⭐⭐ 诚实。2.5 整节 Scrum Guide 细节（三类职责、Increment、DoD）全标 ⭐⭐⭐，对初级岗偏满，Developers ≠ 程序员这条面试该留，其余可标可跳。2.8 标 ⭐⭐⭐ 但不要求动手，星级不诚实。

## 清晰

- 一句话核心是否真能当过滤器：能。「测试的位置由研发生命周期决定，不是开发全部写完才能测」可以筛掉「等提测再出现」的段落。2.9 Git 勉强贴到「证据要留下来」，贴不紧过滤器。2.2 把 ISTQB 七活动与「不要理解成第八步」写在 MiniShop 例子之前，免责声明长于例子。2.5 先写「敏捷不是不要文档」，读者要到第二句才看见敏捷是什么。
- 术语/例子问题：提测、冒烟、确认、回归、DoD / 验收条件有对照例子，口径与第 3 章一致。未教先用的词：2.6「OpenAPI」「金丝雀」；2.7「创建订单（Body 无 `status`）」；2.8「错误码」「并发」「权限场景」。`Body 无 status` 对第 19 章契约是对的，对本章读者是天书。2.1 正文阶段名（需求 / 开发 / 集成与测试）、Mermaid（开发与持续验证 / 集成与系统测试）和 `ch02-where-test-sits`（编码 / 动态测试）三套叫法不完全同词。

## 实操与图

- 实操类型与验收：`practice/README.md` 把 2-1 写成 📖「在 MiniShop 上标出需求→提测→冒烟会落在哪」，产出应进 `exercises/`。章内 2.8 却是一张填满的教师表：无空白、无路径、无完成标准，读完无法判断对错。小练习 1～8 有答案，可作口头验收；练习 9 Git 有「能解释五条命令、提交只含预期文件、不误推」，但命令块假定 `notes.md` 已存在、仓库已 `git init`，没有第一帧该看到什么。没有 `/login` 可抄示例、没有验证码、没有 Postman 个数问题。
- 现有图是否讲难点：三张图标题都能当一句教学，不是「示意图 3」。《冒烟、确认、回归》把三种「再测一遍」拆开，是本章最有用的图；回归文案写「登录、下单、权限」，正文 2.7 写「合法改数量、登录和创建订单」，口径略漂。《V 模型》命题对（成对、别把系统设计对到系统测试），但和正文表几乎重复，没有画出「左边约定 / 右边核验」的空间关系。《测试在研发里的位置》五段管道能讲 2.1，底部却提前讲 V 模型和「左移」，图出现在 2.4 / 2.6 之前。
- 缺图的概念（最多 3 个，要具体到节）：
  1. 2.2 SDLC 包含 STLC（嵌套，不是旁边第二条流水线）
  2. 2.5 DoD（Increment 质量门槛）vs 验收条件（单条故事）
  3. 2.6 左移（需求/设计评审）与右移（发布后监控）画在同一时间线上

### 1. 把场景导入换成 5 步走读

- 目标文件：`chapters/02-software-development-process.md`
- 替换位置：`## 场景导入：一句话需求怎样变成可上线的功能？` 下现有两段
- 拟写：

```markdown
MiniShop 产品经理丢来一句：「购物车里的商品数量可以修改。」
若现在就当上线，测试会卡住：能改成 0 吗？库存 10 件时改成 11 呢？谁来拦？

一次最小走读：

1. **需求**（代码还没有）：问清「不得小于 1、不得超过当前可售库存」，把歧义写成评审问题——这是静态测试。
2. **开发中**：准备库存为 0 / 1 / 10 的数据，等可运行版本。
3. **提测后**：先冒烟（登录、列表、加购还能走通），再测改数量。
4. **修复后**：按原步骤再改一次 11（确认测试）；再看合法改数量、登录、下一单有没有被带坏（回归）。
5. **发布时**：交出已测范围、未测项和剩余风险，而不是「通过」两个字。

后面的 SDLC、Sprint、左移右移，都是给这条走读画地图。公司关卡名字可以不同，位置问题不变。
```

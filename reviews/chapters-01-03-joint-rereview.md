# 第 1～3 章联合严格复审记录

## 复审背景

- 复审范围：第 1 章《软件测试入门》、第 2 章《软件研发流程与测试的位置》、第 3 章《软件测试分类体系》
- 复审原因：对早期模型生成内容进行更高标准的二次检查
- 复审日期：2026-09-08
- 质量依据：Quality Standard v1.0
- 外部基准：ISTQB CTFL v4.0.1、ISO/IEC 25010:2023、The Scrum Guide 2020、Git 官方文档

## 结论先行

三章整体结构和主线可保留，但发现 8 个值得修正的问题，其中包括 2 个会直接造成误解或实操失败的问题：

1. 第 1 章的 Security 与 Safety 中文名称区分不明显；
2. 第 2 章 Git 示例仍引用重命名前的旧文件路径；
3. 第 1 章 Verification 与 Validation 首次出现不符合中英文术语规则；
4. 第 2 章容易让初学者把 Scrum Developers 理解成“程序员”；
5. 第 2 章 Sprint 图把 Daily Scrum 与持续工作放在同一节点，关系不够清晰；
6. 第 3 章“测试方法视角”命名不够精确；
7. 第 3 章把网络条件直接列入兼容性范围，分类不严谨；
8. 第 3 章没有充分说明安全相关功能测试与更广安全测试的目标边界。

上述问题均已修正。

## 分章问题与修正

### 第 1 章

| 问题 | 风险 | 修正 |
| --- | --- | --- |
| “安全性（Security）”与“安全（Safety）”中文相近 | 初学者会认为是同一概念重复列出 | 改为“信息安全性”和“安全保障性”，并解释保护对象差异 |
| Verification/Validation 直接使用英文 | 不符合首次出现术语规范，中文语境也存在译法差异 | 补充教学译法、英文词和实际含义，并提醒以含义为准 |

复审评分：**98/100**。扣分点主要是入门章信息密度较高，但尚未影响理解。

### 第 2 章

| 问题 | 风险 | 修正 |
| --- | --- | --- |
| Git 示例引用 `chapters/02-sdlc-and-testing.md` | 文件不存在，学习者照做会收到 pathspec 错误 | 改为实际路径 `chapters/02-software-development-process.md` |
| Developers 容易被理解为职位名称 | 误以为测试人员不属于 Scrum Developers | 明确它是 Scrum 责任角色，不只指写业务代码的人 |
| Sprint 图把工作与 Daily Scrum 合并 | 容易把 Daily Scrum 当成开发测试阶段 | 改为围绕 Sprint Goal 工作，并用反馈自环表达每日检查与调整 |

复审评分：**99/100**。Git 命令路径已使用仓库实际文件验证。

### 第 3 章

| 问题 | 风险 | 修正 |
| --- | --- | --- |
| “测试方法视角”边界模糊 | 容易与执行方法、测试过程混淆 | 改为“测试技术依据”，强调规格与内部结构 |
| 网络条件直接列入兼容性 | 把测试条件与质量目标混为一谈 | 移出兼容性清单，说明其可作为性能、可靠性或移动场景条件 |
| 权限场景直接作为非功能安全示例 | 忽略安全功能需求也可以进行功能测试 | 增加“按测试目标分类”的边界说明 |
| “95% 请求”表述不够精确 | 容易把请求占比误当成规范指标 | 改为第 95 百分位响应时间，并强调阈值来源 |

复审评分：**99/100**。保留“灰盒”为行业常用描述，同时继续明确其边界因资料而异。

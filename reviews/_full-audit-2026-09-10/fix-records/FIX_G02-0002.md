# FIX RECORD
Audit ID：G02-0002
原问题：08B 点名 RFC 6750 只教了「持有者即可用 / `Authorization: Bearer`」，未写同一份 RFC 的 TLS MUST，也未写禁止把 Bearer 放进可明文发送的 Cookie。MiniShop v1.0 本机 HTTP，且把同一 token 放进无 `Secure` 的 Cookie。
修改文件：`chapters/08b-web-auth-permission.md`
修改位置：§8.12 Bearer 段；本章可运行性说明。
原内容：（摘录）
> Bearer Token 来自 HTTP 认证实践（RFC 6750）。核心含义是：谁持有这个令牌，谁就可以用它访问被允许的资源。
> 当前实现后续请求用这一写法；冻结仪式在第 19 章。
修复后内容：（摘录）
> 同一份 RFC 还要求：带 Bearer 的请求必须走 TLS（HTTPS）；**禁止**把 Bearer 放进可明文发送的 Cookie。MiniShop v1.0 明确不做 HTTPS，登录同时下发 JSON `token` 与 `Set-Cookie: minishop_session=同一串; HttpOnly; Path=/`（无 `Secure`）。这是本机教学范围，不是 RFC 6750 的完整用法，不要抄到生产或写成「已按 RFC 6750 落地」。
为什么这样修：持有者语义写对了，但不能让读者以为明文 HTTP + Cookie 存同一串就是 RFC 6750 用法。v1.0 无 HTTPS 可以是教学范围，必须标明边界。
依据：RFC 6750 §1 TLS mandatory to implement and use；§5.3「Always use TLS (https)」「Don't store bearer tokens in cookies」：bearer tokens MUST NOT be stored in cookies that can be sent in the clear。
是否影响其他章节：ISSUE 原文还列了第 13/16 章，仓库内 `RFC 6750` 仅出现在 08B，本轮只改 08B。分层正确结论不推翻。
验证结果：8.12 同时保留持有者语义与 TLS/明文 Cookie 禁令；可运行性重复「不是完整用法」。
状态：FIXED

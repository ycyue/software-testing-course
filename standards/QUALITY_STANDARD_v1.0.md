# 软件测试课程全局内容质量标准

版本：Quality Standard v1.0  
适用范围：全部章节、练习、项目、代码、图表和面试材料。

## 一、质量目标

每章必须同时满足：技术正确、零基础可理解、工作中可用、能够实践、支持面试与求职。

全书有一条可记住的脊柱：**测试 = 观察 + 判定 + 证据**。各章是在扩展观察通道、写清判定、或留下证据，而不是互不相关的工具清单。读者 README 面向学习者；审查分数、制作流程放在 `docs/COURSE_CONTROL.md` 与 `reviews/`。

遇到冲突时优先级为：

技术准确性 > 实际工作适用性 > 知识完整度 > 初学者可理解性 > 表达美观 > 篇幅。

## 二、知识来源与时效性

优先使用正式标准和官方规范：ISTQB、ISO/IEC、RFC、W3C、WHATWG、OWASP。工具操作优先使用 Python、pytest、Postman、Playwright、Selenium、Chrome DevTools、MySQL/PostgreSQL、Git 和 Linux 官方资料。

软件版本、工具 UI、HTTP 标准、OWASP、ISO 和 ISTQB 内容在发布前检查当前版本，并区分稳定原理与可能变化的操作步骤。

## 三、零基础教学标准

每个重要知识点至少回答：

1. 它是什么？
2. 为什么存在？
3. 测试工程师为什么需要？
4. 实际什么时候用？
5. 怎么使用？
6. 常见错误是什么？

解释顺序优先采用：生活类比 → 简单模型 → 正式定义 → 具体例子 → 工作场景。

禁止定义堆砌。核心概念至少提供一个最简单例子、一个正常例子和一个错误或边界例子。

## 四、技术准确性硬约束

不得教授以下错误绝对化规则：

- GET 不安全、POST 安全
- Cookie、Session、Token 是三种互相替代的技术
- P0/P1/P2/P3 在所有公司含义统一
- 没有发现 Bug 就说明系统没有 Bug
- 测试必须等开发全部完成后才能开始
- 接口自动化 ROI 永远最高

涉及质量、测试原则、HTTP、SQL、接口、权限和自动化时，必须说明适用条件、上下文和边界。

## 五、MiniShop 一致性

MiniShop 是全书唯一主案例。

第 19 章之前，路径、字段、密码规则、验证码、优惠券、支付和订单状态若出现，一律视为**教学约定或技术示例**，必须在正文标明；不得写成已冻结的项目契约。正式冻结以第 19 章 `project/minishop/docs/PRD.md` 与 OpenAPI 为准。冻结之后，后续章节不得随意改变字段、订单状态、接口和业务规则。

后续章节只复习已有概念，不重复大段主讲内容。

MiniShop 最终应包含可运行的前后端、数据库、PRD、OpenAPI、Postman、测试、自动化、日志、Bug 和 README 材料。教材不得虚构不存在的测试结果。

## 六、代码、SQL 和安全

正式代码必须语法正确、上下文完整、命名清楚，并尽可能实际运行验证。不能运行的内容必须标明“伪代码”或“示例结构”。

零基础章节不得无提示地引入未学习的装饰器、继承、异步和元编程。

涉及 UPDATE、DELETE、DROP、TRUNCATE 时，必须说明授权测试环境、明确 WHERE、先 SELECT 验证范围，并优先使用事务或备份。安全测试只允许在自有或明确授权的环境中进行。

## 七、章节结构

每章标题下必须有**一句话核心**（该章要练会的那句话，不是话题清单）。

每章至少对应一个实操练习（`practice/` 可运行脚本，或章内「MiniShop 工作实战」书面实操），并写清：目标、最小命令或产出路径、验收条件、类型（✅ 可运行 / 📖 书面实操 / 🚧 未跑完）。实操要能练会该章那句话，而不是再抄一遍步骤。

每章统一包含：

1. 本章解决什么问题
2. 学习目标
3. 前置知识
4. 场景导入
5. 核心知识
6. MiniShop/工作实战
7. 常见错误
8. 面试角度
9. 小练习
10. 练习答案
11. 本章检查清单
12. 本章总结
13. 下一章预告

知识层级统一使用：⭐⭐⭐ 必须掌握、⭐⭐ 常用、⭐ 了解。

## 八、Definition of Done

每章发布前检查：

1. 目标明确
2. 前置知识正确
3. 无知识性错误
4. 重要信息未过时
5. 无错误绝对化
6. 术语准确
7. 零基础能理解
8. 示例具体
9. 有实际工作场景
10. MiniShop 一致
11. 代码经过验证
12. SQL 操作安全
13. 图表确实帮助理解
14. 知识重要级别明确
15. 常见错误有价值
16. 面试题不是死记硬背
17. 练习覆盖目标
18. 答案与练习对应
19. 检查清单可验证能力
20. 能自然衔接下一章

20/20 可发布；18～19 项修正后发布；17 项及以下不得发布。

## 十、诚实证据

- 克隆仓库、安装依赖、冒烟通过，都不等于实操完成。
- 教材不得把未执行的 GUI、未加压的 JMeter、未拍摄的 DevTools 面板写成已完成。
- 允许结论为「复现了缺陷」或「假设未成立」；负结果也是证据。
- MiniShop 只能标注为个人软件测试实践项目。

## 十一、版本控制规则

每章按“正文初稿 → 质量审查 → 修正版 → 最终评分”的顺序提交。审查记录必须保留发现的问题、严重程度、修改动作、最终评分和剩余风险。完成当前章节并达到发布标准后，才能进入下一章。
